TABLE: MedicalFiles
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Columns
───────
file_id              → Auto-generated UUID (Primary Key)
user_id              → Foreign Key: References Users.user_id
visit_id             → Foreign Key: References Visits.visit_id (Nullable)
file_name            → Original uploaded filename
storage_path         → Supabase Storage path
file_type            → MRI / Prescription / Blood Report / X-Ray
mime_type            → image/png, application/pdf, etc.
file_size            → File size in bytes
upload_date          → Timestamp of upload
analysis_status      → pending / processing / completed / failed
ocr_text             → Extracted text from OCR
created_at           → Record creation timestamp
updated_at           → Last update timestamp

Purpose
───────
Stores metadata for every uploaded medical document. Actual files are stored
in Supabase Storage while this table maintains references and processing status.
This enables the AI to process medical documents for clinical reasoning.

Owned By
────────
Medical Upload Service

Used By
───────
• Upload API
• OCR Pipeline
• Vision AI
• Timeline
• Dashboard

Referenced By
─────────────
• AIAnalysis

Notes
─────
• Files are NEVER stored inside PostgreSQL (only metadata)
• Only storage URLs/paths are saved in the database
• One user can upload multiple files
• AI updates analysis_status after processing
• OCR text extraction is performed asynchronously
• File validation occurs on upload

Example Workflow
────────────────
        Upload File
            ↓
  Store in Supabase Storage
            ↓
    Save Metadata to DB
            ↓
    Trigger AI Analysis
            ↓
    Update analysis_status

TABLE: SymptomSessions
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Columns
───────
session_id           → Auto-generated UUID (Primary Key)
user_id              → Foreign Key: References Users.user_id
session_date         → Date/time of symptom submission
session_type         → initial / follow-up / reassessment
status               → completed / in_progress
created_at           → Record creation timestamp
updated_at           → Last update timestamp

Purpose
───────
Represents a single symptom submission session. Multiple symptoms can belong
to one session, allowing the AI to analyze them as a group and establish
temporal relationships between reported symptoms.

Owned By
────────
Intake Agent

Used By
───────
• Intake Agent
• Clinical Reasoning Agent
• Timeline Agent
• Dashboard

Referenced By
─────────────
• PatientSymptoms

Notes
─────
• Groups multiple symptoms into a single submission event
• Enables AI to understand symptom context and timeline
• One session can contain multiple PatientSymptoms records
• Session type influences AI analysis approach

Example Workflow
────────────────
  Start Symptom Intake Session
            ↓
   User Reports Multiple Symptoms
            ↓
    Create PatientSymptoms Records
            ↓
     AI Analyzes Grouped Symptoms
            ↓
    Generate Clinical Reasoning

TABLE: PatientSymptoms
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Columns
───────
symptom_id           → Auto-generated UUID (Primary Key)
session_id           → Foreign Key: References SymptomSessions.session_id
user_id              → Foreign Key: References Users.user_id
symptom_name         → Name of symptom (as reported by patient)
symptom_description  → Detailed description of symptom
onset_date           → When symptom started
severity             → mild / moderate / severe / critical
duration             → How long the symptom persists
location             → Body part affected (if applicable)
associated_symptoms  → Related symptoms reported
created_at           → Record creation timestamp
updated_at           → Last update timestamp

Purpose
───────
Stores every symptom reported by a patient. Each symptom belongs to a
symptom intake session and serves as primary input for AI clinical reasoning.
Symptoms are the foundation for all subsequent medical analysis.

Owned By
────────
Intake Agent

Used By
───────
• Intake Agent
• Clinical Reasoning Agent
• Timeline Agent
• Dashboard

Referenced By
─────────────
• AIAnalysis

Notes
─────
• Symptoms are entered exactly as reported (no normalization)
• No master symptom table is maintained (flexible symptom names)
• AI interprets symptom names dynamically
• Multiple symptoms can belong to one SymptomSession
• Severity is critical for AI triage and risk assessment
• Temporal data (onset_date, duration) influences diagnostic reasoning

Example Workflow
────────────────
      User Reports Symptom
            ↓
   Create PatientSymptoms Record
            ↓
   Link to SymptomSession
            ↓
   AI Clinical Reasoning Engine Processes
            ↓
   Generate AIAnalysis & Recommendations
